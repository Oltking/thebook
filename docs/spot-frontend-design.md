# v1 spot frontend — design

How the web app changes to trade the new non-custodial spot CLOB (see
`docs/spot-contract-design.md`). The goal is the smallest honest UI that lets a
wallet-connected user trade real `TOKEN/USDT|USDC` pairs.

## What already fits (don't rebuild)
- **Wallet connect + signing** already exist: `@polkadot/extension-dapp`
  (`web3Accounts`, `web3FromSource` signer) via `@gear-js/react-hooks` `useAccount`,
  with tx signing centralized in `providers/MarketDataProvider.tsx`. The human-wallet
  path the spot model needs is already here.
- Layout, theming, toasts, tx-status, account selector — all reusable as-is.

## What changes fundamentally
| Today (testnet) | v1 spot |
|---|---|
| Internal `usd/btc/eth/vara` balances (`GetPortfolio`) | **Real wallet VFT balances** (per-token `BalanceOf(me)`) |
| 3 hardcoded assets | **Curated pairs** from `Spot/GetPairs` |
| No approval step | **`approve` per token** before it can be escrowed |
| Fills update internal balance | Fills credit **claimable balances**; user **withdraws** |
| Join grants $1,000 | No grant; connect wallet, trade what you hold |

## The one new UX primitive: allowance / approve
A spot order escrows real tokens via `transfer_from`, which needs a prior `approve(dex,
amount)` on that token's VFT contract. This is the only genuinely new flow:

- Before the order form is actionable on a given token, read `Allowance(me, dex)`.
- If allowance < needed, show an **Approve** step. Two-tx UX:
  `Approve wUSDT` -> (confirm) -> `Place order`. Offer "approve max" to avoid
  re-approving every trade (common DEX pattern; note the standing-allowance tradeoff).
- Cache/refresh allowance after approve and after each order.

This needs a token VFT client (the token program's own IDL) in the frontend, separate
from thebook's client.

## Data the app now reads
- `Spot/GetPairs` -> the market list (base, quote, decimals, active).
- Per token `Vft/BalanceOf(me)` -> wallet balance; `Vft/Allowance(me, dex)` -> approval.
- `Spot/GetOrderbook(pairId)` -> depth (u128 levels).
- `Spot/GetMyOrders` -> open orders (+ cancel).
- `Spot/GetClaim(token)` -> withdrawable proceeds (+ withdraw).

New hooks: `useSpotPairs`, `useWalletBalances(tokens)`, `useAllowances(tokens)`,
`useClaims(tokens)`. Amounts are `u128` -> use `bigint` end to end; format by each
token's decimals (from the pair), not a global constant.

## View-by-view
- **Market picker** (new, small): replace the BTC/ETH/VARA toggle with a pair selector
  driven by `GetPairs`. Shows base/quote symbols.
- **TradeView** (the big rework): order form (Limit/Market, Buy/Sell) sized in base qty
  with quote total; show wallet balance of the relevant token; gate on allowance with the
  Approve step; submit via `spot.placeLimit/marketBuy/marketSell`. Drop perps/leverage
  from v1 (deferred). Orderbook + my-orders panels read the spot service.
- **PortfolioView**: real wallet balances per listed token; **Claimable** section with a
  Withdraw button per token; open orders with cancel. Remove internal-balance/net-worth
  framing tied to the virtual model.
- **SwapView / PoolsView / perps / Hive agent-money bits**: park behind a flag or remove
  for v1 — they assume the virtual model. Decide per view (SwapView could later route to
  an AMM; Pools/Perps are v2).
- **Landing / onboarding / copy**: strip "free $1,000 / faucet / trade freely / virtual
  balances" everywhere; the message is "connect wallet, trade real tokens."

## Client regeneration (mechanical prerequisite)
`frontend/src/lib/sails.ts` is generated by the **npm `sails-js-cli`** pinned to
`sails-js 0.5.1` — regenerate with that exact version (`npx sails-js-cli generate
thebook.idl -o src/lib/sails.ts`), NOT cargo-sails v2 (incompatible output). Also
generate/obtain a **VFT client** for the token program for balance/allowance/approve.

## Out of scope for v1 (tracked, deferred)
Perps UI, pools/LP, swap routing (RivrDEX watch-item), agent real-money custody UX
(spend limits) — all v2 per `MAINNET.md`.
